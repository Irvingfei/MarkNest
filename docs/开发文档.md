# TOS 7 MarkNest（Markdown 笔记库）开发文档

- **应用 ID**：`marknest`
- **版本**：1.0.0（单一事实来源为仓库根目录的 `VERSION`，改动后必须递增）
- **目标平台**：TOS 7.0 及以上，首发 x86_64
- **形态**：Deb 原生应用，WebUI 以 iframe 嵌入 TOS 桌面
- **后端**：Python 3.10（仅标准库），Unix Socket HTTP 服务
- **前端**：CodeMirror 6（Vite 预构建为单一 IIFE bundle，产物提交进仓库）
- **产物**：`dist/marknest_x86_64.deb`

---

## 1. 这个应用做什么

把笔记以**普通 `.md` 文件**的形式保存在 NAS 的一个共享文件夹里。文件管理器里直接可见、SMB 可访问、由卷快照保留历史版本；应用本身只是这些文件的一个编辑器与索引器。

**索引是派生缓存**，不是事实来源。删掉索引库只会导致一次重建，不丢任何笔记。

## 2. 存储与权限模型

### 2.1 应用自建共享文件夹

官方权限模型规定，Deb 应用应通过平台工具 `ter_share_add` 创建**自己拥有**的共享文件夹：

```bash
ter_share_add -device "$(basename "$VOLUME")" -name "marknest-data" -owner marknest
```

**实测（TOS 7，测试机）**：

| 验证项 | 结果 |
|---|---|
| 创建位置 | `/Volume1/marknest-data`，带 `system.tm_acl` |
| 应用账户读写 | **无需任何授权步骤**即可创建与读回文件 |
| 幂等性 | 重复调用返回同一路径，无副作用 |
| SMB 导出 | `smb.conf` 自动新增 `[marknest-data]`，`browsable/writeable = yes` |

这是整个存储设计的基础。它同时也意味着：**`postrm` 在任何参数下都不删除该文件夹**——笔记是用户自己的文件，而且 `ter_share_add` 没有配套的删除工具，删了就找不回来。这是对「purge 清数据」惯例的**刻意偏离**，已在 `DEBIAN/postrm` 里写明理由。

### 2.2 `preinst` 刻意不加入 `allusers`

笔记应用只碰它自己拥有那一个文件夹，不申请访问操作者的其它共享文件夹。所以 `preinst` **不执行** `usermod -a -G allusers`。这比同类应用的权限更小，审核时无需回答「一个笔记应用为什么要看我的文件夹」。

### 2.3 目录布局

```
/Volume1/marknest-data/            # 应用自建，文件管理器可见
└── users/
    ├── alice/notes/**/*.md
    └── bob/notes/**/*.md
/usr/local/marknest/data/index.db  # 索引：刻意放在共享文件夹之外
```

索引放在应用目录而非共享文件夹，是因为 SQLite 的 `-wal`/`-shm` 兄弟文件出现在用户的文件管理器里只会造成困惑，而且容易被误删。

## 3. 身份模型与残余风险

**每个 TOS 用户一个自己的笔记库。** 服务以单一非特权账户运行，操作系统层面无法区分用户，所以隔离在代码层实现。

### 3.1 ⚠️ 实测更正：平台代理**不转发** `tos_current_username`

最初的设计假设是：TOS 自己的后端服务（`/usr/sbin/filemanager`、`/usr/sbin/storagemanager`）读 `tos_current_username` cookie，而浏览器 cookie 会被转发到应用的 socket，所以沿用同一约定即可。

**这个假设在真机上被推翻了。** 测试机 实测：

| 项 | 结果 |
|---|---|
| 浏览器是否持有该 cookie | ✅ `document.cookie` 里有 `tos_current_username=test` |
| 会话与 CSRF cookie 是否到达应用 | ✅ 到达（否则鉴权会先失败，根本走不到身份解析） |
| **该 cookie 是否到达应用** | ❌ **经 `/v2/proxy/<appid>/` 的请求里没有它** |
| 同样的请求直接打应用 socket | ✅ 带上就正常解析 |

所以：**WebUI 从自己文档里读出该 cookie，再用一个专用请求头 `X-MarkNest-User` 发给后端**；后端优先读该头，cookie 作为回退保留（成本为零，且它是平台自身的约定）。

### 3.2 校验（把身份当不可信输入）

`auth.resolve_identity()`：严格字符集校验（禁 `/` `\` NUL 控制字符、`.`/`..`、超长）+ **必须能通过 `pwd.getpwnam()` 解析出真实系统账户**，否则 `3013`。

### 3.3 ⚠️ 残余风险（如实记录，不粉饰）

**这个身份完全由客户端声明，没有任何服务端绑定。**

两个来源（请求头与 cookie）都由客户端提供，信任等级相同。**已经持有有效平台会话的人可以把值改成另一个用户名，从而访问那个人的笔记库。**

这不是本应用引入的疏漏，而是平台能力的缺失：服务只有一个 unix 账户，操作系统同样无法区分二者，而平台没有提供「按应用、按用户」的身份接口。**真正的修法只能来自平台。**

在上架材料中已如实声明。给操作者的建议：若多人共用且互不信任，请在控制面板收紧 `marknest-data` 的 SMB 访问。

### 4.1 写路径（最容易做错的部分）

**能力探测：读与写是两个独立的 ACL 位，分别实测。**
TOS 7 用 `system.tm_acl` 里的 SPC ACL 管控共享文件夹，**POSIX 模式位已不代表现实**，所以两个答案都来自真正尝试操作：

- 读：`os.scandir` 并**消费一个条目**（scandir 是惰性的，`PermissionError` 在第一次 `next()` 才抛出，不在上下文退出时）
- 写：在**目标目录**里 `mkstemp` → 写一字节 → 删除。写权限挂在**父目录**上，不是目标文件上

**原子写**：暂存文件建在**目标文件自己的目录**里，然后 `os.replace`。

> 这里有个比「失败」更危险的失败方式：`config.tmp_dir` 在 `/usr/local/marknest/data`，与 `/Volume*` 是**不同文件系统**。跨文件系统替换**不会报错**——shell 的 `mv` 会退化成拷贝+删除，Python 的 `os.replace` 才会抛 `EXDEV`。静默的非原子写正是要避免的，所以同目录暂存是硬要求，并有单独的自检断言钉住它。

**符号链接写目标一律拒绝**，不是跟随——跟随就是「库内的写落到库外」的实现方式。

**冲突检测**：`rev = sha256(content)` 作为乐观锁。保存时带回 `base_rev`，不匹配则返回 `3007` 并附当前内容，界面给三个出口（覆盖 / 重新载入 / 另存副本）。超过 8MB 退回 `mtime_ns+size`（更弱，已在代码里注明）。

### 4.2 搜索

启动时**特性检测** FTS5（设备实测 SQLite 3.37.2 且含 `ENABLE_FTS5`，但不假设）。`MARKNEST_FORCE_SEARCH_FALLBACK=1` 可在有 FTS5 的机器上强制走回退路径以便测试。

FTS 表的 `rowid` 直接绑成 `notes.id`，省掉一张映射表。

**FTS5 分词器会剥掉标点**，所以搜 `100_` 会退化成 token `100`，从而命中含 `100%` 的笔记。这是全文检索的本质，但**返回一个并不包含用户所输内容的笔记是不可接受的**。因此：FTS 只负责快速召回候选，再用字面文本过滤一遍。两个引擎对标的点的行为因此一致。

回退路径在 Python 里做子串匹配，**`%` 和 `_` 是字面字符，不是通配符**。

两条路径都强制带 `user = <解析出的用户>`，**不存在跨用户搜索接口**。

### 4.3 索引新鲜度

**不用 inotify。** 共享文件夹是 SMB 面，笔记可能来自 Windows、文件管理器或本应用，`inotify` 在这种挂载上的语义随客户端而变，且每用户一个监听器会翻倍。改用 `mtime_ns + size` 扫描：请求触发时带 2 秒最小间隔，另有 30 秒后台扫描线程。

删除靠**缺席推断**——SMB 侧删掉的文件在这里没有任何事件，唯一能发现的方式就是扫描没看到它。

## 5. 前端架构

### 5.1 模块与加载顺序

```
i18n → ui → api → toshost → vendor.editor → treepane → editorpane
     → previewpane → searchpane → app
```

全部沿用 IIFE + 单全局的约定，无框架、运行时无构建步骤。

### 5.2 构建链（唯一的例外）

CodeMirror 6 必须打包，所以引入 `webui-src/` + Vite。三条硬约束：

1. **`build.py` 绝不调用 Node。** bundle 由开发机跑 `tools/webui_build.py` 产出并**提交进仓库**。Node 只是开发期依赖，绝不进包、绝不进 `Depends`——`Depends: python3, systemd` 必须保持诚实。
2. **固定文件名，不用哈希名。** 缓存失效方案是 `?v=<VERSION>`，`bump_version.py` 断言 `index.html` 里只有一个版本值；哈希文件名会同时破坏这两件事。**也不把版本号注入 bundle**——bundle 是提交物，注版本会让每次递增都使它过期。
3. **过期门禁。** `webui_build.py` 写一个标记文件，内容是 bundle 的哈希**和** `webui-src/` 全部源码的排序哈希；`validate.py` 重算并在不匹配时报错。这正是 `__pycache__` 那个教训在 JavaScript 上的移植——提交的构建产物静默过期，是「修复明明上线了却没生效」那类缺陷的同一形状。

### 5.3 宿主几何

TOS 桌面把窗口家具**画在 iframe 之上**，而不是给应用一个排除了它的客户区。三段区域不可放置交互控件：

| 区域 | 尺寸 | 来源 |
|---|---|---|
| 顶部 | **46px 整宽** | `.tos-dialog-move` 是 `height:40px; width:100%; cursor:move`——**整条顶带**都是拖动面 |
| 底部 | **12px 整宽** | `.tos-dialog-resize-bottom`（高 20px，`bottom:-12px`） |
| 右下 | **18×18** | `.tos-dialog-resize-bottom-right` |

不靠截图目测，直接读设备样式表。`tools/measure_topbar.py` 以**零相交**为断言（不是「padding 等于 46」），扫描 600–1180px 八个宽度。

三栏布局（目录树 / 编辑器 / 预览）让这件事更紧：**只有一条工具栏**，放在唯一的顶栏里，其内容以 `padding-top: calc(var(--host-band-top) + 12px)` 推到带下方，而背景仍从 y=0 起（这样那条带读起来是窗口标题区而不是空洞）。

### 5.4 本地化

- `.lang` 14 种语言（上架硬要求）
- WebUI 三种：zh-cn / zh-hk / en-us，键集**机器校验必须一致**（`webui_check.js` 比对 `I18N.tables`）
- `t()` 在缺键时**返回键名本身**，让遗漏以 `editor.foo` 的形式显现在屏幕上，而不是变成空白
- 后端错误码 → 前端 `err.code<NNNN>` 查表本地化，英文原文仅作未知码兜底

### 5.5 安全

笔记内容是不可信输入——它可能经由 SMB 从网络任何地方写进来。所以：

- markdown-it 配置 `html: false`（笔记里的原始 HTML 不是标记）
- 输出再过一遍 **DOMPurify**（第二层）
- 搜索片段先转义再套 `<mark>`，顺序不可颠倒

`tools/verify_editor.py` 用一条含 `<script>` 与 `onerror` 的笔记断言二者都不执行。

## 7. 手工安装（`dpkg -i`）与 App Center 安装的差异

**实测：手工 `dpkg -i` 之后应用跑不起来——不是应用的问题，是平台还会做两件 `dpkg` 不做的事。**

| 平台在应用中心安装时会做 | 手工 `dpkg -i` | 本项目的处理 |
|---|---|---|
| 解包 `webui.bz2` 到 `<root>/webui` | ❌ 不做 | `postinst` 补上（幂等） |
| 建 `/usr/www/<appid>` → `<root>/webui` 符号链接 | ❌ 不做 | `postinst` 补上（仅在缺失时） |
| 生成 `/etc/nginx/AppAccessControl/AppAccessControl-<appid>.conf`（含鉴权集成） | ❌ 不做 | ⚠️ **刻意不放进 `postinst`**——让软件包去改写 Web 服务器配置风险太大 |
| 把应用登记进平台注册表（启动器可见） | ❌ 不做 | 不处理；上架后由平台完成 |

前两项已在 `postinst` 内，因此 `dpkg -i` 能得到一个「服务在跑、页面能开」的应用。**第三项不会**：没有那份 nginx 配置，`/marknest/` 没有任何路由，请求落到默认处理上返回 301/403。

开发期用 `python _ops/_install_web_route.py --commit` 补上——它从平台已安装的同类应用复制一份并替换应用 ID，正是平台会做的事。

行为上还有一个值得记住的差别：**未登录时请求 `/marknest/` 会 302 到 `/tos/?id=marknest#/`**，也就是桌面自己的「打开某应用」URL。登录后访问它，桌面就会以**嵌入窗口**的方式打开应用——这是自动化验证应用的正确入口（见 `_ops/_live_verify_marknest.py`）。

## 8. 已知限制

1. **每用户隔离是代码层而非操作系统层**（见 §3）2. **代码块不按语言高亮**——`@codemirror/language-data` 会让 IIFE bundle 从 697 KB 涨到 1.75 MB（动态导入被全部内联），第一版去掉了
3. **冲突处理是三选一，不是三方合并**
4. **索引有延迟**：无 inotify，SMB 侧改动要等下一次扫描（最长 30 秒）或手动刷新
5. **附件与 `[[双链]]` 计划在 1.1.0**——后端已预留 `3010`/`3009` 错误码与 `data-line` 之外的 `wikilink` 渲染钩子
